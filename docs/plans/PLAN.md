# Web画面からレシートを登録・編集・保存する実装計画

## 1. 目的と前提

画像登録から、OCR候補の修正・複数タグの選択・保存・再表示までを、ローカルWeb画面で完結できるようにします。必要なAPI・SQLite保存・OCRジョブ管理も実装対象です。

- 現在のOCRエンジン・候補抽出を再利用し、既存のMVP方針を具体化します。
- OCR精度改善を待たずにWeb機能を進めます。候補の適合率改善は[Issue #6](https://github.com/cake2357/house-account-app/issues/6)、追加画像での評価は[Issue #3](https://github.com/cake2357/house-account-app/issues/3)で継続管理します。
- 記録対象は商品名と明細ごとの手動タグです。金額・集計・自動タグ付け・ログイン・外部公開は今回の対象外です。

## 2. 画面と操作

画面は次の2つに絞ります。

| 画面 | 表示・操作 |
|---|---|
| レシート一覧 `/` | 画像登録、サムネイル・登録日時・確認状態・OCR状態の表示。新しい順に20件ずつ表示し、詳細へ移動できる |
| レシート詳細 `/receipts/{id}` | 画像との照合、OCR状態・候補・原文の確認、明細編集、複数タグ、下書き保存・確認保存、OCR再実行、レシート削除 |

**基本の操作**

1. 一覧でJPEG／PNGを1枚選び、「登録する」を押します。
2. 登録成功後に詳細へ移動し、自動で開始したOCRの状態を表示します。
3. OCR成功後、「候補を明細に追加」で候補をまとめて編集欄へ追加します。
4. 商品名を修正し、不要な行を削除します。読み取れなかった商品は手入力で追加します。
5. 明細ごとにタグを選び、「下書き保存」または「確認して保存」を押します。

**編集時の動作**

- 候補は既存明細の末尾へ追加します。編集中の明細に含まれる同じ実行ID・候補IDは重複追加しません。同名の商品は別明細として保持します。
- タグは選択済みのチップと「タグを選ぶ」でコンパクトに表示し、選択欄内で検索・新規作成できます。作成しただけでは明細へ割り当てません。
- OCR処理中も手入力・保存を可能にします。状態の取得はOCR表示部分だけを更新し、編集中の商品名・タグを変更しません。
- 保存中は編集と再送を無効化し、成功した場合だけ保存済み状態へ更新します。保存失敗・409競合時には入力を保持します。
- 入力エラーは該当欄に表示してフォーカスを移し、未保存で画面を離れる際には警告します。
- OCR原文・再実行・削除は折りたたんだ補助操作に配置します。レシート削除には確認を挟みます。

**画面配置**

- 幅900px以上は画像と編集欄を左右に配置します。
- 狭い画面は縦並びにし、画像は折りたたみ・拡大表示に対応します。保存操作は画面下部に置きます。
- 390px幅で横スクロールせず編集・保存できることを確認します。

## 3. 実装構成とインターフェース

### Web・保存基盤

- `app/`にFastAPIのルート・HTTP入出力・Jinja2テンプレート・通常のJavaScript/CSSを配置します。
- `src/house_account/`に画像保存・DB・レシート操作・タグ・OCRジョブ制御を配置し、Web層から呼び出します。
- FastAPI・Uvicorn・Jinja2・python-multipartを追加し、uvの依存定義とロックを同時更新します。multipart受信には[FastAPI公式手順](https://fastapi.tiangolo.com/tutorial/request-files/)に従います。
- SQLiteにレシート・明細・タグ・明細とタグの関連・OCR実行履歴・マイグレーション履歴を保存します。保存先は既存の`HOUSE_ACCOUNT_DATA_DIR`を使用します。
- 番号付きSQLで初期化・更新し、画像や静的ファイルの参照を起動時のカレントディレクトリに依存させません。

### API

既存計画のAPIを実装し、画面から使用します。

| 用途 | APIと契約 |
|---|---|
| 登録 | `POST /api/receipts`：画像と初回OCR待機ジョブを登録し、201でレシートID・実行IDを返す |
| 一覧・詳細・画像 | `GET /api/receipts?page=N`、`GET /api/receipts/{id}`、`GET /api/receipts/{id}/image` |
| OCR開始・状態 | `POST /api/receipts/{id}/ocr-runs`、`GET /api/ocr-runs/{run_id}`。開始は202、処理中の再要求には既存実行IDを返す |
| 明細保存 | `PUT /api/receipts/{id}/items`：`{revision, status, items}`を受信し、保存後の明細・更新番号を返す |
| タグ | `GET /api/tags`、`POST /api/tags`。重複作成は409と既存タグを返す |
| 削除 | `DELETE /api/receipts/{id}?revision=N`。OCR待機中・実行中は409で拒否する |

- 明細入力は`{id, name, tag_ids, source_run_id, source_candidate_id}`とし、新規IDは`null`、既存IDは維持します。
- 詳細には最新OCR状態と直近の成功結果への参照を含め、再試行失敗後も以前の候補を表示できます。
- 明細とタグは一括トランザクションで保存し、配列から除かれた既存明細を削除します。古い`revision`は409で拒否します。
- 商品名1〜200文字・最大200明細、タグ名1〜40文字・1明細20タグまでとします。下書きは0明細、確認保存は1明細以上を許容します。
- タグ名の重複判定はNFKC・前後空白除去・`casefold()`を使用します。
- エラーは入力検証も含めて`{error: {code, message, fields}}`に統一します。

### OCR・画像・起動終了

- SQLiteの待機ジョブをバックグラウンドで順番に処理し、推論は既存の子プロセスを使用します。同時実行1件・300秒制限・画面の状態取得は2秒間隔とします。
- 原文を先に保存してから候補を抽出し、成功・候補0件・推論失敗・抽出失敗・タイムアウト・中断を区別します。失敗時も手入力で保存できます。
- OCR再実行では保存済み明細・タグを変更しません。
- 起動時に保存先の排他ロックを取得し、待機ジョブを再開、実行途中だったジョブを中断扱いにします。終了時は子プロセスを停止してからロックを解放します。起動終了処理は[FastAPIのlifespan](https://fastapi.tiangolo.com/advanced/events/)にまとめます。
- 画像はJPEG／PNG・15MiB・4,000万画素までとし、実体を検証します。元画像を保持し、EXIF回転と長辺最大4,000pxへの縮小を施したOCR入力を別途保存します。
- 登録失敗時のファイル回収、削除後の孤立ファイル回収を実装します。
- `127.0.0.1`・1 workerで起動し、許可Host・更新リクエストの同一オリジンを検証します。OCR文字列・商品名・タグ名は文字として安全に表示します。

## 4. 実装順序とIssue・PR

Web実装に対応する既存Issueはなかったため、実装開始時にテンプレートに沿って親Issueと工程別の実装Issueを作成します。各工程はIssue番号入りのブランチで作業し、前工程のPRマージ後に次へ進みます。

| 工程 | 実装内容 | 完了条件 |
|---|---|---|
| 1. 登録・保存基盤 | DB、画像登録、一覧・詳細、削除、起動入口 | 再起動後も登録画像と一覧・詳細が一致する |
| 2. OCR接続 | キュー、排他ロック、復旧、状態・候補・原文表示 | 成功・失敗・0件・中断を画面で区別できる |
| 3. 明細編集 | 一括候補追加、追加・修正・削除、保存、競合処理 | 修正結果が再表示され、失敗時に入力が残る |
| 4. 複数タグ | 作成・検索・複数選択・解除・永続化 | 選択した明細だけへタグが保存される |
| 5. 通し確認 | ブラウザCI、実機操作、パッケージ確認、文書更新 | 新しい担当者が起動から保存・再表示まで再現できる |

各工程のテストは同じPRで追加します。PRには関連Issue・完了条件ごとの確認結果・未確認事項を記載し、新たな課題は元Issue・PRと関連付けます。GitHub操作ができない場合は未実施として報告します。

## 5. 検証と完成条件

- **保存・API**：実SQLiteと一時保存先で、再起動後の永続性、一括保存のロールバック、更新競合、他レシートのID混入、不正画像、削除・回収を確認します。
- **OCRジョブ**：固定OCRで成功・0件・失敗・原文保持を検証し、実子プロセスでタイムアウト・停止・二重起動・復旧を確認します。
- **ブラウザ**：実APIを通して「登録→候補一括追加→不要行削除・修正→複数タグ→確認保存→再表示」を検証します。手入力、保存失敗、競合、未保存警告、390px表示も対象にします。
- **回帰防止**：タグの自動付与がないこと、OCR再実行で編集中・保存済みの内容が変わらないことを確認します。
- **品質確認**：既存のRuff・整形確認・mypy・pytest・ビルドに加え、PlaywrightのChromiumテストをCIへ追加します。実際に配信された画面と静的ファイルも実機で確認します。

Web機能の完成条件は、サーバー・ブラウザの再起動後も画像・商品名・タグ・確認状態が一致し、OCR失敗時にも手入力で保存できることです。OCR精度の正式な受け入れとMVP全体の完成は、別途残っているIssueの達成状況で判定します。
