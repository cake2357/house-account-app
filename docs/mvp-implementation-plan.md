# 家計簿アプリ MVP実装計画

保存先：`docs/mvp-implementation-plan.md`
状態：工程0を実装中（2026-10-31）。工程1以降は未実装。
工程0の結果は[OCR検証記録](ocr-validation.md)、複数店舗での最終評価は

## 1. 目的と確定した範囲

**レシート画像から商品名を読み取り、人が修正・確認して保存し、購入明細ごとに複数のタグを付けられること**をMVPの完成条件とする。

| 項目 | 方針 |
|---|---|
| 利用環境 | 自分のPC内で動くローカルWebアプリ |
| OCR | ローカルPaddleOCR。画像を外部サービスへ送信しない |
| 記録単位 | レシート内の購入明細。同じ商品名でも別の明細として扱う |
| 記録内容 | 画像、OCR原文、商品名、タグ、登録日時、確認状態 |
| タグ | 全レシート共通の一覧から、明細ごとに0個以上を手動選択 |
| 保存先 | ローカルのSQLiteと画像ファイル |

金額・数量・店名・購入日の構造化、集計、商品マスタ、自動タグ付け、割引計算、ログイン、共有、外部公開は対象外とする。タグの改名・削除・階層化も後続機能とする。

画像は日本語の印字レシートを対象とし、JPEG／PNGを1枚ずつ登録する。PDF・HEIC・複数画像の結合は対象外とする。

## 2. 技術構成とディレクトリ

現在のリポジトリはPython 3.13・uvのテンプレートで、アプリ本体とDBは未実装。新規アプリとして構築する。

- Web：FastAPI、Uvicorn、Jinja2、通常のJavaScriptとCSS。
- 保存：標準ライブラリの`sqlite3`と番号付きSQLマイグレーション。
- 画像：Pillowによる検証とEXIF回転の反映。
- OCR：PaddleOCR／PaddlePaddleをCPUで実行。
- 検証：pytest、httpx、Playwright、既存のRuff・mypy。
- 依存管理：uvを継続し、依存定義と`uv.lock`を同時に更新する。

```text
app/
  __init__.py
  main.py                 # Webアプリ生成・起動終了処理
  dependencies.py         # サービスの組み立て
  schemas.py              # HTTP入出力
  routes/                 # 画面・receipts・ocr・tags
  templates/              # Jinja2テンプレート
  static/                 # JavaScript・CSS

src/house_account/
  config.py               # 設定
  domain/                 # 明細・タグ・OCR結果の型と検証
  services/               # 登録・保存・OCRジョブの制御
  repositories/           # SQL・トランザクション
  storage/                # 画像保存・検証
  ocr/                    # エンジン・子プロセス・候補抽出
  migrations/             # 番号付きSQL

scripts/
  prepare_ocr_models.py    # モデルの事前取得
  evaluate_ocr.py          # 実画像による評価

tests/
  README.md               # テストの実行方法とデータの扱い
  conftest.py             # 保存先・アプリ生成などの共通fixture
  unit/                   # 業務規則・候補抽出の単体テスト
  integration/            # API・SQLite・ファイル・ジョブの結合テスト
  browser/                # Playwrightによる画面操作テスト
    conftest.py           # テストサーバーの起動・終了
  fixtures/               # 架空のOCR結果・期待値・合成画像

main.py                   # appを起動する薄い入口
docs/mvp-implementation-plan.md
```

依存方向は`app → src/house_account`とし、業務処理からWeb層を参照しない。補助スクリプトは`src/`の処理を呼び出し、OCRや保存処理を重複実装しない。

パッケージ設定に両方のPythonパッケージとテンプレート・静的ファイル・SQLを含める。ファイル参照は実行時のカレントディレクトリに依存させない。

保存先は`HOUSE_ACCOUNT_DATA_DIR`で指定し、既定値をリポジトリ内の`data/app/`とする。モデルは`artifacts/ocr-models/`へ保存する。DB、画像、実レシートのOCR結果、モデルはGit管理対象外とする。

## 3. 実装する動作とインターフェース

### 画面と操作

画面はレシート一覧と詳細の2画面とする。

1. 画像を登録すると詳細画面へ移動し、OCRを開始する。
2. 処理中・成功・失敗を表示する。
3. 成功後、「候補を明細に追加」で商品名候補を編集フォームへ取り込む。
4. 商品名の修正、行の追加・削除、タグの複数選択を行う。
5. 「下書き保存」または「確認して保存」で永続化する。
6. 一覧や詳細を開き直して、保存内容を確認できる。

タグは明細の編集画面で作成できる。作成だけでは割り当てず、選択して明細を保存したときに確定する。同じ商品名からタグを継承しない。

画像と明細を照合できる配置にし、OCR原文は折りたたんで表示する。保存失敗時は入力を保持し、未保存の変更がある状態での画面移動には警告する。390px幅でも操作できるレイアウトとする。

### OCR処理

OCRと商品名抽出を分離する。

- エンジンの境界は`recognize(image_path) → OcrResult`とし、文字列・座標・信頼度・モデル情報を返す。
- 初期モデルは`PP-OCRv5_server_det`と、日本語対応の`PP-OCRv5_server_rec`を明示指定する。モデルの対応情報は[公式ガイド](https://www.paddleocr.ai/main/en/version3.x/pipeline_usage/OCR.html)に基づく。
- モデル取得は準備スクリプトで行う。通常の読み取りではローカルモデルを使用し、未準備なら準備手順を案内する。
- 抽出処理は座標から行を組み立て、末尾の価格表記を分離し、日時・電話番号・合計・税・支払等の行を除外する。商品名に含まれる単語の部分一致だけで除外しない。
- 価格と対応しない文字行や信頼度0.80未満の候補は「要確認」として残す。名称の推測や自動確定は行わない。
- 原文は候補抽出より先に保存する。抽出に失敗しても原文を確認できる。

OCRはSQLiteに保存したジョブを順番に処理し、子プロセスで実行する。同時実行は全体で1件、タイムアウトは1件300秒。画面は2秒間隔で状態を取得する。

状態は`queued → running → succeeded / failed`とする。候補0件は正常終了として区別し、手入力を案内する。アプリ再起動時は待機ジョブを再開し、実行途中だったジョブは中断エラーにする。

同じ保存先への二重起動をOSのファイルロックで拒否し、ロック取得後に復旧処理を行う。Uvicornは1 workerで起動する。

**OCRの再実行は新しい結果を作るだけで、保存済みの商品名・タグを変更しない。** 再試行に失敗した場合も直近の成功結果を参照できる。

### データと保存

| テーブル | 役割 |
|---|---|
| `receipts` | 画像情報、登録日時、確認状態、更新番号 |
| `receipt_items` | レシートに属する明細、順序、商品名、OCR候補の出典 |
| `tags` | 安定したタグID、表示名、重複判定用の名前 |
| `receipt_item_tags` | 明細とタグの多対多関係 |
| `ocr_runs` | OCR実行状態、原文、候補、モデル情報、エラー |
| `schema_migrations` | 適用済みのスキーマ版 |

IDはUUIDとし、明細の名前を修正してもIDを維持する。タグ割り当ては明細IDとタグIDの複合一意制約で重複を防ぐ。

保存時の規則は次のとおりとする。

- 商品名は前後空白除去後1〜200文字。1レシート最大200明細。
- タグ名は1〜40文字。重複判定はNFKC正規化・前後空白除去・`casefold()`で行う。
- タグは1明細につき0〜20個。存在しないタグIDは拒否する。
- 下書きは明細0件を許容し、確認保存には1件以上を必要とする。
- 明細全体とタグ割り当てを1トランザクションで保存する。
- 既存明細はIDで更新し、削除された行だけを取り除く。
- 更新番号`revision`が一致しない保存は409で拒否し、入力を保持して再読み込みを案内する。
- OCR候補は実行IDと候補IDで出典を記録し、同じ候補の二重取り込みを防ぐ。
- 確認済み明細も再編集可能とする。「下書き保存」で下書きへ戻り、「確認して保存」で確認日時を更新する。

### API

| メソッド・パス | 契約 |
|---|---|
| `POST /api/receipts` | 画像をmultipartで受信し、201でレシートIDを返す |
| `GET /api/receipts` | 登録日時の降順で一覧取得。20件ずつ表示 |
| `GET /api/receipts/{id}` | 明細・タグ・revision・最新OCR状態を取得 |
| `GET /api/receipts/{id}/image` | 保存画像を取得 |
| `POST /api/receipts/{id}/ocr-runs` | 202で実行IDを返す。処理中なら既存の実行IDを返す |
| `GET /api/ocr-runs/{run_id}` | 状態・原文・候補・エラーを取得 |
| `PUT /api/receipts/{id}/items` | `{revision, status, items}`で明細全体を保存 |
| `GET /api/tags` | 共通タグ一覧を取得 |
| `POST /api/tags` | タグ作成。重複時は409と`error.existing_tag`を返す |
| `DELETE /api/receipts/{id}?revision=N` | レシートと関連データを削除。OCR処理中は409 |

明細入力は`{id, name, tag_ids, source_run_id, source_candidate_id}`とする。新規明細のIDは`null`。保存配列に含まれない既存明細は削除する。既存明細の出典は変更できない。

エラー形式を`{error: {code, message, fields}}`に統一する。HTTP入力検証でも同じ形式を使用する。

### 画像とローカル運用

画像は最大15MiB・4,000万画素とし、拡張子だけでなく実体を検証する。元画像を保持し、EXIF回転を反映した長辺最大4,000pxのOCR入力画像を別途作成する。

登録失敗時は今回作成したファイルを回収する。削除はDB更新後に画像を削除し、削除失敗による孤立ファイルは次回起動時に回収する。

サーバーは`127.0.0.1`で待ち受け、許可Hostと更新リクエストの同一オリジンを検証する。画面へ出すOCR文字列・商品名・タグ名はエスケープする。

## 4. 実装順序と受け入れ条件

| 工程 | 作業 | 完了条件 |
|---|---|---|
| 0. OCR検証 | Python 3.13・macOS arm64で依存解決、モデル準備、実画像の読み取りと候補抽出 | 実画像から文字・座標・候補を取得し、モデル・依存版・所要時間を記録できる |
| 1. 保存基盤 | パッケージ構成、設定、DB、画像登録、一覧・詳細・削除 | 再起動後も画像とレシート情報が残る |
| 2. OCR接続 | ジョブ制御、状態API、候補・原文表示、再試行 | 成功・失敗・0件・中断を区別して表示できる |
| 3. 明細編集 | 候補取り込み、追加・修正・削除、下書き・確認保存 | 編集結果が再表示で一致し、古いrevisionの保存を拒否する |
| 4. 複数タグ | タグ作成、選択・解除、保存 | 1明細へ2個以上付けて保存でき、他の明細へ影響しない |
| 5. 引き継ぎ | 通しの検証、CI、README、計画書更新 | 新しい担当者がセットアップと基本操作を再現できる |

PaddlePaddleの公式資料にはmacOS arm64・Python 3.13対応が記載されているが、周辺依存を含む実機動作は工程0で確認する。[公式インストール資料](https://www.paddlepaddle.org.cn/documentation/docs/en/install/pip/macos-pip_en.html)

依存解決または推論に問題がある場合はエラーを記録し、実装の前提を見直す。未検証のままOCRを完成扱いにしない。

自動テストでは次を確認する。

- 商品行の抽出、価格の分離、合計等の除外、同名商品の別行保持。
- 複数タグ、重複タグ、タグ未選択、他レシートのID混入、保存失敗時のロールバック。
- 明細IDの維持、revision競合、OCR再実行による編集済みデータの保護。
- 不正画像、容量超過、OCR失敗・タイムアウト・0件・再起動・二重起動。
- ブラウザでの「登録→候補修正→複数タグ→確認保存→再表示」と390px表示。

通常CIでは固定OCR結果を使い、Ruff・整形確認・mypy・pytestを実行する。ブラウザテストも隔離した保存先とテスト用OCRで実行する。

テストの配置、実装順序、CIへの追加時期は第6節に従う。各工程の機能とテストは同じPRで追加し、工程5でまとめて作り始めない。

実OCRは別途、3店舗以上・計5枚以上・合計30商品行以上で評価する。正解商品行と候補の対応を記録し、全画像を通算した行抽出の適合率・再現率80%以上、各画像300秒以内を初期の受け入れ基準とする。誤字による修正件数は別に記録する。

最終的に、サーバーとブラウザの再起動後も画像・商品名・タグ・確認状態が一致し、OCR失敗時にも手入力で保存できることを確認する。

## 5. ブランチ戦略

### 基本方針

`main`を統合先とし、作業ごとに短期間のブランチを作成する。常設の`develop`やリリース専用ブランチは設けない。`main`は、その時点で実装済みの機能が起動・検証できる状態に保つ。

テンプレートと本計画の初回コミットは`main`へ記録済み。以降は最新の`main`からIssue番号を含む作業ブランチを作り、Pull Request（PR）を通して取り込む。工程0は`spike/1-ocr-validation`で作業する。

### 工程とブランチ名

| 工程 | ブランチ名の例 | 主な変更 |
|---|---|---|
| 0. OCR検証 | `spike/00-ocr-validation` | 依存・モデル・実画像の検証、評価スクリプト、検証記録 |
| 1. 保存基盤 | `feat/01-storage` | パッケージ構成、DB、画像保存、レシートAPI |
| 2. OCR接続 | `feat/02-ocr-jobs` | ジョブ制御、状態表示、再試行 |
| 3. 明細編集 | `feat/03-item-editing` | 候補取り込み、明細編集、保存と競合検知 |
| 4. 複数タグ | `feat/04-item-tags` | タグ作成、複数選択、割り当て保存 |
| 5. 引き継ぎ | `chore/05-handover` | 通しの検証、CI整備、READMEと計画書の更新 |

原則として工程0から順に取り込み、依存する工程は前工程のマージ後の`main`から開始する。工程0の検証に失敗した場合は、失敗内容と前提の見直しを記録してから工程1以降へ進む。試行用のコードは整理し、再利用するスクリプト・依存設定・検証記録を取り込み対象にする。

1工程が大きい場合は、単独で検証できる単位に分ける。例えば保存基盤は`feat/01-db`、`feat/01-receipt-api`の順に取り込む。独立した作業は並行してよいが、未マージのブランチから依存ブランチを重ねない。修正は`fix/<内容>`、文書のみの変更は`docs/<内容>`を使う。

### マージと完了の条件

1. PRには対象工程、変更後の動作、実施した検証と結果、未検証・未達の項目を記載する。
2. 最新の`main`を作業ブランチへ取り込み、競合を解消してから必要な検証を行う。依存変更では`pyproject.toml`と`uv.lock`を同時に更新し、`uv sync --locked`で確認する。
3. 既存CIのRuff・整形確認・mypyを通す。pytestとブラウザテストは対象機能の追加に合わせてCIへ組み込み、導入後はマージ条件とする。実OCRの検証結果は別途PRへ記載し、通常CIの成功だけで実画像検証済みとはしない。
4. 差分と該当する受け入れ条件をレビューする。個人開発ではセルフレビューを可とする。工程を分割したPRでは対象部分の完了を確認し、工程全体の完了は第4節の条件をすべて満たした時点で記録する。
5. 条件を満たしたPRを`main`へSquash mergeし、取り込み済みの作業ブランチを削除する。修正が必要になったら最新の`main`から新しいブランチを作る。

番号付きSQLマイグレーションはマージ前に番号の重複を確認し、`main`へ取り込み済みのファイルは書き換えず、追加のマイグレーションで変更する。DB・レシート画像・実OCR原文・モデルは各ブランチでもGit管理対象外とし、検証記録に個人情報を含めない。

MVPの全受け入れ条件を満たした`main`のコミットに`v0.1.0`タグを付ける。問題が見つかった場合は修正PRを作成し、緊急に取り消す必要がある場合は対象コミットをrevertするPRを作成する。DB変更を含む場合は、コードのrevertだけではデータが戻らないため、追加マイグレーションまたは停止中に取得したバックアップからの復元を併せて検討する。

## 6. テスト戦略と実装計画

### 現状と方針

工程0の単体テスト・架空OCR fixture・合成画像・pytest設定を実装し、CIへpytestを追加した。結合・ブラウザテストとhttpx・Playwrightの直接のdev依存は未導入。以下は工程1以降も含めたテスト計画とする。

テストは`tests/`へ集約し、第3節の動作・入力制約と第4節の受け入れ条件を検証する。関数を呼べることや内部の呼び出し順だけを確認するテストは避け、入力に対する結果、保存内容、エラー後の状態を確認する。特にデータ消失、別明細への影響、自動タグ付けの混入、OCR再実行による上書きを優先して防ぐ。

### テストの種類と配置

| 種類・配置 | 対象と代表的な確認 | 実行方法 |
|---|---|---|
| 単体：`tests/unit/` | 商品行の抽出、価格分離、除外条件、同名商品の別行保持、低信頼度候補、名前の正規化、文字数・件数の境界値 | pytest。DB・Webサーバー・実OCRを起動しない |
| 結合：`tests/integration/` | API契約、マイグレーション、明細とタグの一括保存、revision競合、画像保存と回収、OCRジョブの復旧 | pytestとhttpx。実際のSQLite・一時ファイルを使い、OCRエンジンをテスト用に差し替える |
| ブラウザ：`tests/browser/` | 登録から確認保存・再表示までの操作、入力保持、エラー表示、タグの選択・解除、390px幅の操作 | pytest-playwrightとChromium。実サーバー・実APIを通して検証する |
| 実OCR評価：`scripts/evaluate_ocr.py` | 実画像の認識・候補抽出の精度、所要時間、モデルと依存版 | モデル準備済みのmacOS arm64で明示的に実行する。通常のpytest・CIから分離する |

### 共通のテスト基盤

- `tests/conftest.py`に一時保存先、アプリ生成、DB初期化、テスト用OCRのfixtureを用意する。pytestの`tmp_path`でテストごとに保存先を分け、利用中のDB・画像・モデルに触れない。
- 結合テストはファイル形式のSQLiteへ本番と同じマイグレーションを適用する。再起動テストでは同じ一時保存先を再利用し、アプリとDB接続を作り直して永続化と復旧を確認する。
- 固定OCR結果は文字列・座標・信頼度・モデル情報を持つ架空データとし、期待する候補を併記する。正常・0件・低信頼度・例外を再現できるテスト用エンジンを依存注入し、通常テストで実モデルの取得や推論を行わない。
- タイムアウトはテスト用に短い期限を設定し、停止待ちの子プロセスで再現する。二重起動は同じ一時保存先を使う別プロセスで確認する。単なるモックの返り値だけで終了・ロック・復旧処理を検証済みとしない。
- ブラウザ用fixtureは空きポートでサーバーを起動し、起動確認後に操作を始め、失敗時も終了処理を行う。画面の状態を条件に待ち、固定秒数の待機に依存させない。UI側のAPI応答は差し替えず、サーバー側のOCRだけを差し替える。
- `tests/fixtures/`には架空データと合成画像だけを保存する。実レシート画像・実OCR原文・個人情報はGit管理外とし、実画像の評価には識別用の番号を使う。

### 必須の回帰テスト

| 対象 | 確認する結果 |
|---|---|
| 明細・タグの保存 | タグ0個・複数個、同名商品の別明細、選択解除、明細ID維持、空の下書き、確認保存の最低1明細、確認済みからの再編集を扱える。保存途中の失敗では明細とタグをともにロールバックする |
| 不正入力・競合 | 上限ちょうどと上限超過、存在しないID、他レシートの明細ID・OCR出典、出典の変更、古いrevisionを検証する。拒否時は保存済みデータを変更せず、規定のエラー形式を返す |
| 手動タグ付け | タグ作成・OCR・候補取り込み・同名商品の追加ではタグを自動付与しない。正規化後に同じタグ名は409と既存タグを返し、重複割り当てを保存しない |
| OCRと候補 | 候補の二重取り込みを防ぐ。再実行で編集済み明細とタグを変えず、再試行失敗後も直近の成功結果を参照できる。抽出失敗時も原文が残る |
| ジョブと再起動 | 同時処理は1件で、処理中の再要求は既存実行IDを返す。成功・失敗・0件・タイムアウトを区別し、再起動時は待機を再開、実行途中を中断扱いにする。二重起動では復旧処理を実行しない |
| 画像と削除 | JPEG／PNG、破損・偽装画像、容量・画素数の境界、EXIF回転、縮小、元画像保持を確認する。登録失敗時の回収、関連データの削除、処理中の削除拒否、孤立画像の起動時回収を確認する |
| HTTPと表示 | 一覧の順序とページ分割、画像取得、入力検証を含むエラー形式を確認する。不正Host・別オリジンからの更新を拒否し、OCR文字列・商品名・タグ名のHTMLを実行せず文字として表示する |
| 画面の操作 | 登録→候補修正→複数タグ→確認保存→再表示を通す。OCR失敗時の手入力、保存失敗・409時の入力保持、未保存の移動警告を確認する。390px幅で画像と明細を照合し、編集・保存できる |

### 実行方法とCI

導入時に`pyproject.toml`へpytest設定を追加し、通常の探索先（`testpaths`）を`tests/unit`と`tests/integration`に限定する。ブラウザテストはパスを指定して別途実行する。httpx・pytest-playwrightはdev依存へ追加し、`uv.lock`も更新する。以下は基盤導入後の実行コマンドとする。

```sh
# 単体・結合テスト
uv run --locked pytest

# 種類を指定して実行
uv run --locked pytest tests/unit
uv run --locked pytest tests/integration

# ブラウザの準備と画面操作テスト
uv run --locked playwright install chromium
uv run --locked pytest tests/browser --browser chromium
```

CIではロック済み依存を使用し、Ruff・整形確認・mypyに加えて単体・結合テストを実行する。ブラウザテストは別ジョブに分け、Linuxでは`uv run --locked playwright install --with-deps chromium`で実行環境を準備する。失敗時のスクリーンショットとトレースを調査用に保存する。ジョブを導入した時点からPRの必須確認とし、空のテスト実行や無条件skipで成功扱いにしない。

MVPの完了判定には、通常CIの成功に加え、第4節の実画像評価と、利用環境でのサーバー・ブラウザ再起動後の保存内容確認を必要とする。テスト件数やカバレッジ率だけで完了とせず、各受け入れ条件の検証結果・実行環境・未検証項目をPRと引き継ぎ記録に残す。

## 7. 将来の割引設定と引き継ぎ

MVPでは、安定した明細ID・タグIDと多対多の割り当てを用意する。割引用のテーブルや画面は先行実装しない。

将来はタグIDの組み合わせを条件とする独立した割引ルールを追加する。条件は「すべて付いている」「いずれかが付いている」「どれも付いていない」を表現できる構造とし、タグ名やタグ側の割引チェックには依存させない。

金額・税・丸め・ルールの併用は割引機能を追加するときに定義する。確定した計算結果には適用ルールと計算条件を保存し、後のタグ・ルール変更で過去の計算結果を自動変更しない。

実装時は、まず本計画で既存の計画書を更新する。READMEにはモデル準備、起動、保存先、アプリ停止後のデータ一式バックアップ、OCR失敗時の対処を記載する。完了報告では、実装済み・自動テスト済み・実画像検証済み・未達を区別する。
